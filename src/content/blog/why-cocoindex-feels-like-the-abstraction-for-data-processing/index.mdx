One of the most awesome things about open source projects is getting to observe how their designs (and sometimes, their entire vision) change in public. I've been following and using [CocoIndex](https://cocoindex.io/) since its early days, and it's been fascinating to see this kind of evolution firsthand.

CocoIndex v0 was built around dataflows[^dataflows]. As they've evolved into v1, much of that thinking has moved toward a new abstraction called **processing components**, that compose over both structured and nested data. In my previous post [on why I love using CocoIndex](5-reasons-i-love-cocoindex-and-why-you-should-try-it), I touched on some of the cool vi features at a high-level.

Watching that transition reminded me of something I wrote about earlier while learning about [DSPy](/blog/learning-dspy-1-the-power-of-good-abstractions/): getting the level of abstraction right (in any framework) is _hard_. As I've become more familiar with CocoIndex's v1 API, I've realized that the same principles that made me like DSPy (for working with LLMs) also apply to CocoIndex, but for building incremental data processing pipelines.

What's interesting about CocoIndex is that the overall great developer experience comes from multiple layers of the stack _all working well together_: nested data can remain nested, processing components provide a natural unit of composition, and incremental computation determines what work actually needs to happen when data changes. Taken in isolation, none of those ideas is especially surprising on its own. The interesting part is how they all come together, making the framework a joy to use.

These are the core ideas to unpack in this post, so let's dig in!

## Why tables became the default

Working with data in tables became the default for good reasons. Tables give us a compact language of columns, filters, joins and aggregations, while exposing enough structure for query engines to optimize aggressively on top of them. From relational databases to DataFrames like Fenic, Spark and Daft, and columnar formats like Parquet, Lance and Apache Arrow, this model gives engines a lot to work with: vectorized execution over batches, column pruning, predicate pushdown, query planning and efficient parallel scans.

The combination of a familiar programming model and a highly optimizable execution model is a big reason tables have become so dominant across the data infra landscapte today.

<TableDefaultFlow />

As an application developer, it's important to not conflate the **execution model** (used by the engine) with the **programming model** (used by the developer). We're not just storing data; we're describing the desired transformations too. For tables, this is typically expressed in terms of column projections, joins, aggregations and other operators the compute engine can reason about. The _storage_ shape and the _logical_ shape used by the engine, may be different.

## The three shapes of application data

Application data can be thought of as having three different shapes:
- **Storage** shape is where the data lives,
- **Logical** shape is how the application assembles and reasons about it,
- **Computation** shape is the unit of work we actually want to transform.

Those three often line up, but they don't have to. A product might be stored across Postgres and object storage, represented in code as one nested Product, and processed as one unit.

<DataShapesFlow />

Not every application object is naturally tabular. A product might combine metadata, images, variants and descriptions into one logical object. At that point, the question is simple: should we reshape the problem to fit the engine, or should the engine let us keep the shape of the problem?

```json title="one logical Product assembled from two storage systems"
{
  "product_id": "trail-runner-01",
  "metadata": {
    "name": "Trail Runner",
    "brand": "Northstar"
  },
  "images": [
    { "uri": "s3://catalog/trail-runner-01/front.jpg", "view": "front" },
    { "uri": "s3://catalog/trail-runner-01/side.jpg", "view": "side" }
  ],
  "variants": [
    { "sku": "TR-01-BLK-42", "color": "black", "size": 42 },
    { "sku": "TR-01-BLK-43", "color": "black", "size": 43 }
  ]
}
```

The computation might then be as simple as "process this product and its parts." A tabular system can absolutely express that, but the translation may involve exploding nested collections, carrying product identity through the transformation, then regrouping or joining the results. Those operations are useful, but some of that vocabulary is coming from the engine rather than the problem itself.

Storage shape answers **where the data lives**. Logical shape answers **what the application thinks it is**. Computation shape answers **what we actually want to transform**. They often line up, but they don't have to. That leaves us with the more interesting question: what structure does an execution engine actually need from us?

## CocoIndex asks for a different kind of structure

- Introduce the **processing component** as the key bridge between application code and incremental execution.
- Explain that CocoIndex still needs structure from the developer; it doesn't make execution concerns disappear.
- Describe the information the framework needs:

  ```text
  this is a stable unit of computation
  this input changed
  this computation depends on it
  this target state belongs to this component
  ```

- Give examples of valid processing-component boundaries:
  - A database row.
  - A product.
  - A file or page.
  - An image.
  - A domain entity assembled from multiple sources.
- Separate two ideas that are easy to conflate:
  - The component defines the boundary at which work can be tracked and updated.
  - The Python value inside that boundary can remain flat, nested, multimodal, or otherwise shaped around the domain.
- Make the key point: the execution boundary doesn't have to dictate the shape of the underlying Python value.
- Transition from the individual primitive to the combination that makes the programming model compelling.

## Why the combination matters

- State explicitly that processing components alone aren't the whole abstraction.
- Present the model as a combination:

  ```text
  ordinary Python values
          +
  processing components
          +
  declarative incremental computation
  ```

- Clarify what the developer owns:
  - The domain model.
  - The component boundary.
  - The transformation logic.
  - The desired target state.
- Clarify what CocoIndex owns:
  - Change detection.
  - Dependency tracking and reuse.
  - Synchronization with the target.
  - Component lifecycle.
  - The execution machinery needed to keep target state current.
- Connect this back to abstraction level: the framework asks for information that is meaningful to both the application and the runtime.
- Explain why no single feature tells the full story; the value comes from how the pieces reinforce one another.
- Transition to the asymmetry this model creates between flat and nested problems.

## The asymmetry I find compelling

- Begin with the easy case: when a problem is naturally tabular, the logical object can simply be a flat record.
- Explain that CocoIndex doesn't require a more exotic representation for this case.
- Contrast that with hierarchical or multimodal problems:
  - The domain model can become richer without forcing the developer into a different programming vocabulary.
  - The processing boundary can remain aligned with the logical entity.
- Center the section on this formulation:

  > A flat record is an easy special case of CocoIndex's model. A deeply nested domain object isn't always an easy special case of a table-oriented programming model.

- Qualify the comparison carefully:
  - Tables remain excellent when the computation itself is relational.
  - Joins, aggregations, scans, and columnar analytics aren't awkward edge cases; they're the natural strength of relational systems.
  - The argument is about preserving domain shape when the computation isn't naturally relational, not replacing tables everywhere.
- Transition from this flexibility back to the broader question of which structure a framework asks developers to provide.

## What CocoIndex gets right

- Return to the broader abstraction philosophy from the opening.
- State the shared constraint: every performant data framework needs the developer to expose enough structure for the engine to do its job.
- Make the distinction about **which** structure is exposed:
  - Columnar systems expose tables, columns, expressions, and relational operators so the engine can plan queries and execute them efficiently.
  - CocoIndex exposes stable computational boundaries, dependencies, and desired target state so the engine can execute incrementally.
- Explain what remains comparatively unconstrained in CocoIndex: the application's logical model and the ordinary Python transformations applied to it.
- Avoid turning this into a simplistic declarative-versus-imperative comparison; CocoIndex combines declarative lifecycle and state management with developer-owned Python computation.
- Tie the contrast back to the product example and show why the distinction is useful in practice.
- Land the section on the central insight: CocoIndex's abstraction feels different because the structure it asks for is about incremental computation, not about reshaping the domain into the engine's preferred data model.

## The payoff

- Return to DSPy and close the loop with the opening argument.
- Restate the standard for a good abstraction:
  - It doesn't hide the most complexity by default.
  - It asks the developer to describe exactly the information the system needs.
  - It leaves the developer thinking in terms of the problem they're actually solving.
- Connect DSPy and CocoIndex without claiming their internals or domains are equivalent:
  - DSPy lets the developer express the intended behavior of an LM program without hand-authoring every prompt-level mechanism.
  - CocoIndex lets the developer express domain computation and desired state without manually managing every incremental-execution mechanism.
- Emphasize the shared feeling rather than forcing a one-to-one technical analogy.
- End on the thesis:

  > **I can express my intent without having to think like the engine underneath me.**

[^dataflows]: A dataflow represents computation as a graph of sources, transformations, and outputs, letting the engine track dependencies and propagate changes. CocoIndex v0 exposed that model through a static DSL and separate type system, which made dynamic control flow, arbitrary Python values, and runtime-defined topology harder to express. CocoIndex's [v1 announcement](https://cocoindex.io/blogs/cocoindex-v1/) explains the design transition in detail.
